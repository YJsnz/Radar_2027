# 信息波 RX1 与 RM2027 接收程序复核

日期：2026-11-16。项目基线：`7d4a027`。参考目录：用户提供的
`/home/geqingyu/最新接收端_20261116/最新接收端/RM2027/receiver/`。
本轮检查源码、安装目录和已有 IQ，没有重启接收机、修改射频参数或进行新采集。
实机丢包与长时稳定性仍未验收，README 对应父项保持未勾选。

## 结论

信息波滤波与 GFSK 解调参数已对齐，剩余的实质差异集中在异常帧恢复、比特缓冲与搜索、实时回调负载，以及设备初始化和切换方式。不能仅凭参数相同，就认定两个完整接收程序的实时表现相同。

本轮离线复现了异常长度等待和大批比特截断两处问题；尚无出问题时的原始 IQ、比特批次大小和缓冲时间记录，不能把它们直接认定为用户观察到的 72% 估计丢包或一分钟后下降的根因。

## 发现的差异

### 1. 异常长度恢复：已复现阻塞

RM2027 的 `protocol.py:87` 在等待完整帧前，先丢弃 payload 长度大于 128 的候选头。
当前 `core/rm_protocol.py:263` 只检查 `frame_length < 9`；无符号长度加 9 后不会小于 9，因此这条检查不能排除过大长度。

若噪声候选的 CRC8 恰好通过且长度异常，当前实现会等待该长度，期间后续正常帧被挡在缓冲区中；若长度超过 4096 字节缓冲上限，可能直到旧数据被缓冲裁剪才重新同步。

本轮构造一个 CRC8 正确、payload 长度为 65535 的异常头，后接 10 个正常 0x0A03 帧，均按 15 字节输入：当前实现输出 **0 帧**、保留 315 字节；RM2027 输出 **10 帧**、缓冲为空。
这是软件异常恢复差异，尚未证实实机发生过同类异常头。

### 2. 比特搜索和缓冲：已复现效率差异及截断

RM2027 的 `phy.py:224` 按比特位置从前向后同时比较正常和反相接入码，找到即返回。
当前 `core/rm_protocol.py:382` 分别搜索正常和反相模式后选择最早命中；即使正常模式在缓冲开头命中，也可能继续扫描后面的反相模式，再为下一个包重复搜索。批次较大时有额外扫描开销。

另一个独立差异是 `push_bits()` 在解析前先把缓冲裁剪到 `max_bits`；比赛配置为 16384。RM2027 没有这个解析前裁剪步骤，而是在找不到接入码时保留尾部。

对同一段 42548 比特的干净实录：

| 每批比特 | 当前有效帧 | RM2027 有效帧 | 有效帧内容／顺序 |
|---|---:|---:|---|
| 22 | 92 | 92 | 一致 |
| 256 | 92 | 92 | 一致 |
| 4096 | 92 | 92 | 一致 |
| 20000 | 75 | 92 | 当前发生截断 |

单次离线计时中，4096 比特分块的当前解析耗时约 0.598 秒，RM2027 约 0.065 秒；22 比特分块约 0.240／0.124 秒。这里只计同步与组帧，不含射频、DSP、IQ 诊断和 ROS 发布；单次计时随机器负载变化，不能直接当作实机吞吐或丢包预测。
20000 比特为主动构造的超限输入，尚未观测到实机 GNU Radio 回调达到该大小。

### 3. 实时工作量不同：待同流测量

两边都在 GNU Radio 的 Python `work()` 路径内完成比特同步与组帧。
RM2027 随后把业务帧放入列表，由 Qt 每 250 ms 调用 `take_frames()` 并更新界面。
当前回调还直接执行 `frame.to_dict()`、JSON 编码、业务桥接和 ROS 发布。

当前另有原始／滤波后两路 Python IQ 回调，每批都计算幅度、相位、均值、方差等诊断；频谱发布受周期限制，但这些逐批诊断没有同样的限频。比赛配置的频谱发布周期为 0.04 秒。
原始 IQ 还在快照解码关闭时先调用 `data.copy()`，然后 `_buffer_iq_samples()` 才返回。
RM2027 把原始 IQ 直接接到 GNU Radio Qt 频谱／瀑布图，没有这两路 Python IQ 诊断回调。

这些开销可能影响实时调度，但目前没有同源流量、缓冲积压或采样缺口证据证明其导致本次丢包。不能把所有额外开销都归咎于 ROS，也不能仅凭整机 CPU 尚有空闲排除某条回调变慢。

### 4. Pluto 初始化和运行切换仍不同

- 当前源通道参数为 `[True, True]`，参考为 `[True, True, False, False]`；两者意图均为第一路复数 RX，尚未做该项硬件 A/B，不能直接判定它导致丢包。
- 当前启动脚本先通过 IIO 写入并回读端口、频率、模拟带宽及增益；参考程序主要由源对象设置。当前 Python IIO 绑定没有 `set_bandwidth`，`_set_iio_rx_bandwidth()` 实际走 `set_filter_params("Auto", ...)` 回退，不能把配置字段 540 kHz 当作运行后的硬件带宽回读。
- 当前启动配置增益仍为 32 dB，参考界面截图为 10 dB；此前项目运行状态也已报告 10 dB。不过 `get_rx_gain_diagnostics()` 返回的是 `self.Gain` 缓存值，运行状态本身不等于新的硬件回读。
- RM2027 在切换波源时停止调度并新建解调器／组帧器；当前多个 setter 可直接修改正在运行的流图，不完整重建 AGC、时钟恢复与组帧状态。固定频点运行时不能据此解释周期性下降。

### 5. 业务解析和显示统计

两边有效槽位和信息波命令长度一致，但输出结构不同：当前发布保留诊断字段的 ROS JSON 并进入融合，RM2027 输出界面用的中文字段。
当前在帧完成后做业务长度校验；本轮已有实机窗口的命令长度失败为 0，没有证据表明新赛季字段解析是 CRC16 失败的原因。

参考界面最近一秒帧数按 250 ms 批量取帧时刻统计；当前 Dashboard 按 ROS 收到有效帧的时刻统计。两者短时 Hz 显示可以不同，但不能解释 CRC8／CRC16 错误增加。
Dashboard 的“估计发送／前级丢失”来自 CRC8 保护的序号缺口，不是独立发射端计数；重复、乱序、长间隔重置会影响该估算。

## 本轮验证与先前验证的补充

先前 `/tmp/compare_info_rx.py` 只切换 DSP 解调器，两种输出的比特都交给本项目组帧器，未完整对照参考组帧器。本轮补上真正的 `PhyDeframer`／`RadarProtocolDecoder`。

对已有 2 秒、4000000 个 complex64 采样的 IQ 重新解调：两边本次均输出 42548 比特且逐位相同，再交给各自的同步和组帧链，均得到 92 个 CRC 有效帧，完整帧哈希及顺序一致。该段仍为先前的干净实录，不是新抓到的故障时段。
在同一比特流中用固定随机种子 20261116 注入 0.2%／1% 独立翻转，再按 256 比特分块，两边分别输出相同的 52／11 个有效帧。这是构造的硬判决误码，不代表射频信道模型。
具体计数见 [复核数据](pluto_rx1_bench_20261116/rm2027_decoder_recheck.json)。

没有改运行代码，本轮未重跑全量单元测试和 ROS 构建。复核结束时 Dashboard API 已不可连接，进程列表也未见两套接收程序；没有自动恢复或抢占设备。

## 后续处理优先级

1. 修复接收路径的异常长度等待，并保证不改变串口其他合法长报文的处理。
2. 消除解析前静默裁剪；搜索改成按位置同时检查两种极性，验证分块边界不影响结果。
3. 增加可限长的原始 complex64 IQ 及比特分块诊断，从同一流做参考与项目双解码；测量回调耗时及样本连续性后，再决定 IQ 诊断降频与发布解耦。
4. 对齐初始化和切换生命周期，补做超过一分钟的同条件实机测试，再评估是否可以关闭相应 TODO。

现有比赛录制在滤波后取样，默认降至 1 MS/s、按块缩放保存 CI8，不是原始 2 MS/s complex64。不能直接把它作为两套完整前端的原始输入并重复滤波。此前提出通过该录制分支取得原始 IQ 的方案不充分；本轮没有降低磁盘保护或开始该录制。
