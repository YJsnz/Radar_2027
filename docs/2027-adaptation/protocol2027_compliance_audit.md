## 修复前实际复现的差异（2026-11-10 历史记录）

以下为修复前纯软件检查的诊断样例，未发送串口或 ROS 指令。列表中的实现缺陷已按上表修复并在 2026-11-11 回归；这些内容只用于记录问题来源，不代表当前仍存在。

1. **0x0305 保留字节被填入坐标。** 在两种阵营下，同时调用 `core/radar_integration.py::build_0305_payload` 与 `vision/RM_serial_py/ser_api.py::build_data_radar_all`，输入 2 号坐标 (102,202)、6 号坐标 (106,206)。偏移 4/6/16/18/28/30/40/42 的 uint16 结果均为 `[102,202,106,206,102,202,106,206]`，应按仓库发送约定置零。两条路径都有该差异。
2. **0x0A01 保留数据进入有效机器人缓存。** 在偏移4/6写入 (12,34)，偏移16/18写入 (56,78)，经过解析 → `RefereeBridge` → `RadarFusionState` 后，得到 `B2.valid=true` 和 `B6.valid=true`。这是保留位置诊断输入，不代表官方会发送这些非零值；它证明本地语义隔离缺失。
3. **合法 0x0A05 导致易伤主要状态失效。** 构造 47B 帧、姿态=3、四台主要状态均=0，桥接输出四个正确键 `opponent_heavy/opponent_infantry_3/opponent_infantry_4/opponent_sentry`。在接收年龄=0秒时，`AutoDoubleVulnerabilityDecision._enemy_main_status()` 返回 `({}, False, 0.0)`。原因是 `double_vulnerability.py:17` 仍要求 `opponent_hero`；该函数遇到缺键会使整组状态无效，影响全部区域候选。
4. **备用协议路径仍是旧尺寸。** `len(build_data_decision(0,'R')) - 6 == 8`，官方要求 13；兼容适配器的 `ctypes.sizeof(RadarInfoData) == 1`，官方 0x020E 数据为 8B。radio 主路径正确，不能据此认为所有启动/通信模式都正确。
5. **错误长度仍生成状态事件。** 将 CRC 正确但仅 1B 的 0x020E、20B 的 0x0003 交给 `RefereeBridge.process_frames()`：顶层长度标志为 false，仍分别发布 `RadarDecisionSync` 与 `GameRobotHP`。radio 串口节点的部分处理会检查有效标志，但桥接输出和视觉 ROS 消费没有统一隔离；应保留诊断原帧并禁止其更新权威状态。
6. **发射样例仍含旧角色保留数据。** 固定随机种子1，`random_payload_for_command()` 生成的 0x0A01 保留坐标、0x0A02 offset2、0x0A03 offset6 均可非零。0x0A05 的保留增益块已通过字段上限0正确清零，不应把它与前三个样例生成器混为一谈。
7. **0x0234 核心实现确认已有迁移。** 实际目标编号为 `[1,3,4,7]`，红方接收者 `(1,3,4,7)`，蓝方接收者 `(101,103,104,107)`。但节点定时器仍乘6，状态中的待发送数仍从6扣减，若配置每接收者3Hz则实际18帧/秒、四接收者每组约4.5Hz。发送循环本身按实际接收者列表长度结束，不会因此按六人索引越界。

## 当前限制与尚未验收项目

- **队端私有0x0234约定：**官方没有定义载荷。当前软件的四目标掩码和接收者映射必须与队端实现确认，不能凭软件测试推断队内实际互通。
- **RF 参数：**规则手册印刷p114 / PDF p115明确写干扰波具体参数后续发布。`radio_config.py` 和接入码仍来自2026配置。本地2027协议给出了0x0A01～0x0A06载荷，不能据此证明2026调制、频点、带宽或接入码是2027官方配置，也不能凭空改成另一组参数。
- **命中事件：**规则§5.2印刷p72 / PDF p73说明受击方常规链路与攻击方雷达无线链路都有命中信息，但所附协议的0x0A01～0x0A06表中没有攻击方命中事件的命令和载荷定义。0x0206是“主控模块→对应机器人”，不能直接假设它是其他机器人的命中信息广播给雷达。
- **0x0A04红蓝语义与异常枚举：**0x0003的R/B前哨及0x0A04的R/B区域名是绝对侧，激活状态及部分控制度又是己/对方相对语义；0x0A04异常枚举诊断仍需补全，不能把整个0x0A0x系列归为单一坐标/阵营语义。
- **实机互通：**尚未做红蓝切换、真实裁判串口抓帧、机会消耗回读、无线电空口参数验证或比赛现场闭环。

## 不应当作雷达适配阻塞的其他命令

命令表必须同时核对发送方、接收方和数据链路。未实现手册里的每个命令，不等于雷达接口不符合。

- 0x0002、0x0101、0x0104可能到达全体/己方全体机器人。当前通用串口接收器可保留CRC有效的原始帧，但未提供全部业务字段解析；比赛结果、场地事件、判罚展示可按业务需要增加，不能把“尚无展示”说成“串口无法接收”。
- 0x0204和0x0206的接收对象是对应机器人，0x0209是己方装有RFID的机器人。不能要求雷达天然收到全队的这些消息；若需要队内转发，另行定义来源、序号和时效。
- 0x0311属于自定义终端经图传发送给对应机器人，当前项目没有使用该链路；其60B变化不是雷达常规串口/无线信息波接入的必要改动。

1. 已完成的软件协议项仍须在取得设备与官方/队端信息后，进行红蓝切换、裁判串口抓帧和裁判回读。
2. 收到官方RF参数后，更新带版本号的射频配置并验证接入码、调制、频率、带宽及接收性能。
3. 从正式上游取得攻击方命中事件载荷定义，再接入自适应装甲算法；不得用0x0206或Dashboard合成数据替代真实来源。
