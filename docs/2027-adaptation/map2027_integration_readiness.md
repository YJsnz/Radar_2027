## 1. 结论

**素材已足够开始 2027 地图的蓝方软件接入和标定准备；还不足以完成红蓝双方实机标定与完整比赛闭环。**

带地胶底图、同尺寸两层掩码、CAD 坐标参考和蓝方两层各六个候选点已具备。下一步可在独立的 2027 资产配置／预设入口上接通显示、点位导入和同侧掩码选择；当前代码尚无这样一套完整、已验证的 2027 运行档案。正式投影仍需真实相机对应点和重新计算的矩阵，不能沿用旧矩阵。

从整个雷达系统看，2027 模型验收、真实命中事件、裁判／RF 实机联调也未完成。无线电处理此前由用户暂缓，本次只记录状态。

## 3. 已定位的代码与配置缺口

### 3.1 标定预设格式尚未接通

`vision/calibration_presets.py` 当前读取 `{"version": 2, "presets": [...]}`，每个方案具有名称、阵营、每层点数和地图点。候选 `points_B.json` 是独立工具输出格式，不能直接替换预设库。

本次实际调用 `load_presets(points_B.json)` 得到“预制方案文件缺少 presets 列表”；用其 `map_points` 调用现有 `make_preset()` 可在内存构造六点／层的蓝方方案，但没有写入预设库。现有库仍是 `blue`、`red人` 两个旧方案。

正式接入应明确地图版本／校验值、阵营与预设绑定。当前预设规范化只保留既有字段，不能假定额外加入 `map_profile` 就会自动被验证或保留。

### 3.2 主程序仍加载 2026 资产，掩码只有一个路径

`vision/config.yaml` 的 `paths.map_images` 仍为：

```yaml
red: images-2026/red.jpg
blue: images-2026/blue.jpg
mask: images-2026/map_mask26.jpg
backup: images-2026/image_2026.jpg
```

`vision/main.py` 按阵营选择竖图和矩阵，但无条件读取同一个 `mask` 路径。红蓝 mask27 不能只换一张后假定另一侧也正确。`backup` 则用于横向落点展示，需要一同选择 2027 横图并核对显示坐标方向。

应整体绑定：阵营、竖图、横图、同侧掩码、点位、矩阵；不在本次覆盖用户配置。尚无真实新矩阵时，可以完成加载／显示和虚拟坐标检查，不能用旧矩阵给真实相机输出 2027 定位。

### 3.3 Dashboard 也需要更换地图

`radio/apps/match_rx/web/index.html` 初始图片和 `app.js` 的红蓝切换仍引用 `image_2026_red_bottom.jpg`、`image_2026_blue_bottom.jpg`；网页静态资源也仍为 2026 图片。

只改视觉地图会导致本地与网页显示不同赛季场地。后续需同步资产、方向、替代文本与缓存版本，核对同一组参考坐标在两端显示一致。

### 3.4 新矩阵及地图版本绑定未完成

`vision/calibration.py` 保存两张单应矩阵，以及 `image_points`、`map_points`、相机模式、图像尺寸、内参档案 ID。当前不会同时写入地图和 mask 的版本／哈希；`camera_calibration.py` 主要检查相机模式、尺寸和当前启用时的内参 ID。

已有检查不能替代“旧赛季矩阵拒绝用于新地图”的绑定。还需处理去畸变开启／关闭的双向一致性，详见 [投影精度审阅](map2027_projection_accuracy_review.md)。本次不更改两层算法。

当前正式标定窗口仍采用固定布局，地图被缩放到 550×900 后点选；独立选点工具的分辨率适配并未自动应用到正式窗口。导入已规范的浮点地图点可避免再次在缩略图中手点带来的量化，但相机点采样和正式界面操作仍需检查。

### 3.5 录制与回放缺少完整资产版本链

`vision/main.py` 的录像清单记录会话、存储、编码和内参档案 ID，尚未记录当前地图、mask、点位、矩阵的版本／SHA-256。视觉遥测也没有附带地图档案标识。

后续接入需要让标定、比赛、Dashboard 和录制／回放知道自己使用哪套资产；仅在图片文件名中写 2027 不足以复现当时的坐标结果。

### 3.6 视觉角色与旧预测配置仍需逐消费者核验

当前 `armor_confirmation.allowed_numbers` 仍包括 2，`blind_zone.roles` 仍为 1/2/7，`vision_telemetry.ROBOT_ROLE_IDS` 仍遍历 2/6 容器；新赛季 radio 最终有效位置槽已按 1/3/4/7 处理。保留容器与有效机器人含义需要区分，不能因为更换地图就宣称整条视觉链已完成角色迁移。

后续应检查检测类别、可输出编号、预测目标、遥测、融合及最终发送的一致性，明确保留槽不会成为有效比赛目标。该项是本次读代码发现的接入核验项，没有在本次修改角色逻辑。

## 4. 推荐接入顺序与验收

| 阶段 | 可以开展的工作 | 通过条件／仍需素材 |
|---|---|---|
| 1：蓝方软件接入 | 使用已有底图、蓝方 mask、候选点，增加受控的 2027 资产选择及预设转换，接通本地／网页显示和版本记录 | 无需先取得真实矩阵即可检查素材加载；新旧资产不得混用，同一组虚拟参考点在两端方向一致。 |
| 2：本机相机标定 | 固定镜头、对焦、ROI、分辨率，采集实物棋盘图并核验内参，再采集这十二个相机对应点 | 地图点与相机点顺序一致，生成新矩阵及来源档案；保留未参与拟合的检查点。 |
| 3：蓝方实车闭环 | 识别→定位→遥测→融合→地图显示／记录，按允许条件联调发送 | 独立点、实车停位、坡口和高地误差有记录；核验检测锚点、保留槽及重启后的档案一致性。 |
| 4：红方与比赛验收 | 独立确认红方可视点，重新采集／求解；完成真实模型、裁判和 RF 联调 | 两侧分别验收，记录实际相机安装与资产版本；完整比赛闭环仍依赖未确认的外部接口和实测素材。 |

现有程序在关闭去畸变时也可以用对应点拟合单应矩阵，真实 K/D 的缺失不是单应求解公式的必要输入缺失。但按本项目“优先标定准确度”的要求，应先固定并核验图像域，避免随后换内参后重做外参；没有相机对应点则确实无法求出真实图像到地图矩阵。
